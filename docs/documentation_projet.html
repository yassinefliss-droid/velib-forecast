Vélib' Forecast

Documentation du projet : architecture, problèmes rencontrés et résolutions, résultats réels
État au 21 novembre 2026. Les chiffres proviennent d'exécutions réelles ; ce qui n'a pas été vérifié est signalé comme tel.

1. Objectif et périmètre

Collecter la disponibilité des stations Vélib' Métropole (flux GBFS ouvert, sans clé d'API), construire un pipeline de données reproductible et contrôlé, puis prévoir à 1 heure le nombre de vélos disponibles par station en le comparant à une baseline naïve de persistance.

Ce qui est fait : collecte, contrôles qualité, entrepôt BigQuery, marts dbt, orchestration Airflow (en partie). Ce qui reste : le modèle de prévision, qui nécessite plusieurs jours d'historique. Aucune métrique de prévision n'existe à ce jour.

2. Architecture

API GBFS Vélib'
   |  toutes les 5 min (cron ; DAG velib_collect dans Airflow)
   v
Extract (requests) -> Transform (Pandas) -> Load SQLite --> contrôles qualité (data_quality_log)
                                              |
                                              |  velib.bq : charge les snapshots absents (rattrapage)
                                              v
                                        BigQuery : raw_station_status, raw_station_information
                                              |  dbt, toutes les heures (DAG velib_transform)
                                              v
                    stg_*  ->  dim_station, fct_station_status, fct_station_5min,
                               mart_features, mart_hourly_profile
                                              |
                                              +--> modèle (à venir) --> fct_forecast
                                              +--> dashboard Streamlit

ETL ou ELT ? Les deux. La collecte est un petit ETL (Pandas type et aplatit le JSON avant l'écriture). Le chargement dans BigQuery est quasi brut, et les transformations analytiques se font en SQL dans l'entrepôt avec dbt, donc en ELT.

6. Choix de conception à savoir expliquer

  • Grain explicite de chaque table (écrit en commentaire dans chaque modèle dbt) : station et snapshot, station et créneau de 5 min, station, jour et heure.
  • Grille régulière de 5 minutes avant les variables retardées : « il y a 60 minutes » n'a de sens que sur des créneaux alignés. Les retards manquants restent NULL.
  • Taux de remplissage (vélos / capacité) pour comparer des stations de tailles différentes ; capacité invalide donne NaN, pas de division par zéro.
  • Seules les stations opérationnelles entrent dans les profils ; les autres restent dans la base.
  • Deux DAG : collecte toutes les 5 min, transformations toutes les heures. catchup=False : l'API ne donne pas le passé. max_active_runs=1 : pas de collectes simultanées sur SQLite.
  • La carte du tableau de bord lit la table brute, pas les marts, qui ont jusqu'à 1 h de retard.

7. Préparation aux questions d'entretien

Pourquoi la clé d'idempotence utilise-t-elle l'horodatage du flux plutôt que datetime.now() ?
Avec l'heure d'exécution, deux passages sur le même flux produiraient deux clés différentes et donc des lignes dupliquées. Avec l'horodatage du flux, les mêmes données ont la même clé et la base ignore le doublon.
Que font INSERT, INSERT OR IGNORE et INSERT OR REPLACE si la clé existe ?
Erreur et arrêt du lot ; ligne ignorée ; ligne écrasée. On ignore pour les mesures (une mesure passée ne change pas), on remplace pour la dimension des stations (nom ou capacité peuvent changer).
Pourquoi donner .venv/bin/python dans le cron ?
Cron s'exécute avec un environnement minimal : il n'active pas le venv et n'a pas ton PATH. Sans chemin explicite, il utilise un Python sans les bibliothèques.
Pourquoi journaliser les anomalies plutôt que supprimer les lignes ?
Supprimer fausse l'historique et masque des informations réelles. Une station hors service explique des erreurs de prévision ; la supprimer rendrait le modèle faussement bon.
Pourquoi un taux de remplissage, et que se passe-t-il si on oublie de convertir de UTC vers l'heure de Paris ?
Le taux rend comparables des stations de capacités différentes. Sans conversion, les pics sont décalés de 1 h ou 2 h selon la saison, et les profils par heure sont faux.
BigQuery ne vérifie pas les clés primaires : comment rendre le chargement idempotent ?
En comparant les snapshot_ts déjà présents à ceux à charger, et en chargeant seulement les manquants. Alternatives : un MERGE, ou un identifiant de job déterministe. En SQLite, c'est une contrainte du moteur ; ici, c'est du code.
Pourquoi charger les snapshots manquants plutôt que seulement le dernier ?
Si BigQuery est injoignable une heure, « le dernier » perdrait les snapshots intermédiaires, alors que le rattrapage les envoie au passage suivant. Démontré : 5 snapshots rattrapés d'un coup.
ETL ou ELT ?
Hybride : ETL pour la collecte (Pandas avant l'écriture), ELT pour l'analytique (SQL avec dbt dans BigQuery, à partir de données brutes conservées pour pouvoir rejouer les transformations).
Pourquoi deux DAG, et pourquoi catchup=False ?
Les rythmes diffèrent (5 min contre 1 h) et reconstruire les marts toutes les 5 min est inutile. L'API ne donne pas le passé : rattraper des exécutions manquées ne retrouverait aucune donnée.
Pourquoi ne pas remplir les NULL de la cible, et comment éviter la fuite d'information ?
La cible NULL des créneaux récents signifie « futur non observé » : la remplir par 0 ou par la dernière valeur fabriquerait une fausse réponse. Pour la fuite : les variables retardées n'utilisent que le passé, et la validation est temporelle (entraîner sur le passé, tester sur le futur), jamais aléatoire.

8. Limites connues

  • La collecte dépend d'une machine allumée : Airflow en local apporte l'orchestration, pas la disponibilité 24 h/24. Chaque interruption laisse un trou définitif.
  • Peu d'historique : profils non interprétables, modèle non entraînable de façon sérieuse pour l'instant.
  • Bac à sable BigQuery : expiration des tables (60 jours, d'après ma connaissance de la documentation, à revérifier) et opérations restreintes.
  • Airflow « standalone » avec SQLite : montage de développement. dbt-core en préversion.
  • Les tests automatiques utilisent des données synthétiques : ils valident la logique, pas le format réel de l'API ni BigQuery.
  • Les contrôles qualité ne détectent pas encore les trous de collecte.
